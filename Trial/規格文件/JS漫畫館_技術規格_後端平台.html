1架構的三條分界線

整體原則：帳戶層沿用遊戲、內容層漫畫自訂。漫畫館是同網域的子路徑（/comic），不是子網域，登入狀態與平台幣才能零成本共用。

1.1 直接沿用（漫畫館不碰）

帳號 SSO、平台幣錢包的查餘額、充值金流、客服系統。漫畫館只呼叫，不複製一份。

平台幣絕對不能有第二本帳。

1.2 需要改造（遊戲站側的工項，要排進他們的時程）

服務要改什麼為什麼
平台幣錢包扣款要支援冪等鍵，並提供退款 API沒有冪等鍵，網路重試與使用者連點都會重複扣款；沒有退款 API，開通權益失敗就無法補償
交易帳本加 site 欄位，查詢支援站別與類型篩選歷史紀錄是同一本帳、分頁只是篩選；充值屬平台層級，兩個站別都要回傳
兌換碼要能發放漫畫館的優惠券，並補一筆「贈送」進帳本否則兌換後餘額接不上
通知中心支援 work:{workId} 與 filter:{...} 兩種深連結型別指名作品的通知要能直接跳作品頁
錢包那一項是整個購買流程的前置條件。如果現有錢包沒有冪等扣款與退款，訂單服務無法開工，時程會整段往後推。這是第一件要去確認的事。

1.3 漫畫館新建

作品目錄、搜尋與排行、定價 Offer、訂單、優惠券、權益／書櫃／進度、閱讀串流，外加一套營運後台（建檔、轉檔切片、定價、排程上架）。

2API 設計的五個原則

  1. 作品一律以 workId 為 key，路徑、參數、回傳都不出現作品名。
  2. 購買範圍 scope 一路貫穿：single（單卷買斷）／vol（單冊）／set（整套）／ch（單話）／bundle（整部）。定價、優惠券適用判斷、訂單、權益開通全部靠它對齊。
  3. 寫入金額的請求一律帶冪等鍵。POST /comic/orders 用 Idempotency-Key 標頭，往下對錢包與券的呼叫一律以 orderId 當冪等鍵。
  4. 折抵金額由後端重算。前端算只為了即時顯示，傳上來的金額一律不信任。
  5. 主按鈕的文字是算出來的。前端不寫死「購買」或「開始閱讀」，而是由 GET /comic/entitlements/{workId} 的結果 ＋ 商品型態決定（立即购买 → 开始阅读 → 续看第 N 话 → 重新阅读）。

3購買的交握順序與補償

鎖券 → 扣款 → 開通權益 → 核銷券 → 訂單 PAID
這個順序不可以改。任何一步失敗都要往回退。
失敗點處理
券鎖定失敗回 409，請使用者重選
扣款失敗（餘額不足）解鎖券 → 回 402 並引導充值。充值完成要回到同一筆購買
開通權益失敗退款 ＋ 解鎖券 ＋ 訂單標記 REVERSED

扣款成功後由錢包服務寫交易帳本（site=comic, kind=消費），漫畫館不自己寫帳。

REVERSED 的訂單必須在對帳報表裡查得出來，否則這類失敗會變成無聲的客訴。

3.1 付款完成要同時發生的三件事

  1. 作品寫入權益書櫃的「已購」
  2. 歷史紀錄多一筆消費
  3. 用掉的那張優惠券從帳號扣除

4優惠券

4.1 規則欄位（必須機器可讀）

{
  id   : 'cp1',        // 唯一識別，結帳扣券用
  t    : '单本 9 折券',  // 顯示名稱
  kind : 'pct',        // pct = 打折 ｜ amt = 定額折
  val  : 10,           // pct：折幾 % ｜ amt：折多少平台幣
  max  : 50,           // pct 專用：折抵上限
  min  : 300,          // amt 專用：門檻金額
  sc   : ['single'],   // 適用購買 scope 陣列；null = 全站
  exp  : '2026.11.30',
  sub  : '单卷单行本买断适用，最多折抵 50 平台币'
}

4.2 折抵計算

pct :  min( floor(價格 × val / 100), max )
amt :  價格 >= min ? min(val, 價格) : 0

「可用」＝購買類型對得上，而且實際折得到錢。滿額券沒到門檻時不回傳，不是回傳但標示不可用。

折抵不可信任前端。實際扣款金額與券的核銷一定要後端重算與驗證。上線要擋過期券。目前假設一次只能用一張；若要允許併用，必須先定義疊加順序與上限。

4.3 兌換碼

  • 兌換碼換到的是平台幣或優惠券，不是訂單折扣，所以不在結帳頁。
  • 兌換成功要同時補一筆「贈送」進交易帳本，否則餘額接不上。
  • 成功回應要夠前端顯示「這次拿到什麼」（前端用畫面上方的浮層提示列出內容）。
  • 失敗要分得出原因：代碼無效／已過期／已使用過。
  • 前端從購買彈窗點條款／退款政策後返回，要能原樣回到同一筆購買（含已選的券），所以彈窗的參數由前端自己保存，不需要後端配合。

6.1 作品

欄位說明

6.2 權益與進度

權益以作品為單位，裡面記每一冊／話的擁有狀況；進度分成兩種，兩者都要回傳，前端才算得出按鈕文字。

欄位意義用在哪
已購的冊／話哪些單位有權益（含免費話）作品頁、冊數列表、閱讀器權益檢查
開過的最高話／冊在閱讀器實際開啟並顯示過的最高單位（鎖話、鎖冊不計）「續看」的目標、列表的「已讀」標記
讀到章末的最高話／冊已經讀到該單位最後一頁區分「讀完 → 買下一個」與「讀一半 → 續看目前這個」
單卷的閱讀旗標未讀 / 閱讀中 / 已讀完單卷單行本沒有話／冊可記，書櫃要靠它分狀態
最後購買時間 / 最後閱讀時間書櫃的「最近購買」「最近閱讀」排序
購買不預先推進進度。確認購買只寫權益；進度要等真的載入該話／冊才更新。

6.3 書櫃三分頁的判定

分頁條件
續讀進度 > 0 且 還沒把擁有的內容讀完。讀完的退出續讀、留在已購；連載更新或多卷出新刊時自動回到續讀
已購有任一權益
收藏加過愛心，與是否購買無關

6.4 交易帳本

  • 每一筆帶 site（comic / game / both）與 kind（消費／充值／贈送／訂閱／簽到）。
  • 充值是 both：屬平台層級，兩個站別的查詢都要回傳。
  • 每一筆要帶當下餘額，最新一筆的餘額＝錢包餘額，整本帳才連得起來。
  • 查詢條件：站別 × 類型 × 時間區間（最近 90 / 30 / 7 天）。

7閱讀串流與內容保護

  1. 開閱讀器時重新檢查權益，免費話與試閱範圍也走同一支檢查。
  2. 建立閱讀工作階段後才發圖片網址。
  3. 回傳：頁面清單 ＋ 簽名短效圖片網址（綁會員、綁工作階段、數分鐘到期）＋ 使用者專屬浮水印參數。
  4. 保護手段：簽名短效網址、切片打散重組、使用者專屬浮水印、逐頁載入、停用右鍵。
  5. 進度回寫要節流；伺服器端是唯一真相。
付費內容只做串流、不提供原始下載。內容保護的強度（浮水印是否必須、切片打散到什麼程度）要和法務／版權方確認後才動工——轉檔管線重做的成本很高。

8內容上架流程

建檔 → 設定商品型態 → 轉檔切片（非同步）→ 定價 → 狀態標示 → 試閱範圍 → 排程上架 → CDN 預熱
  • 轉檔是非同步佇列，失敗要退回待處理清單並通知營運，不能卡死上架流程。
  • 狀態標示規則：完結才標「完结」，單行本未完結不標狀態，每話連載標「连载中」。
  • 封面角標：左上只有 X% off，右下狀態；NEW（近 30 天上架）由前端放在標題右側。
  • 連載更新＝新增話次後回到轉檔，完成再推播給收藏者。
  • 下架要保留已購使用者的權益——這是第一版就要定義的規則（見第 10 節待確認）。

9時程

42 個工項、六個階段、總計 289 人日、18 週。試算表的 B1 是「專案啟動日」，改那一格每個工項的日期會跟著重算，要換成實際的 kickoff。

9.2 關鍵路徑

M0 規格凍結 → 錢包冪等扣款 → 訂單服務 → 購買彈窗 → 整合測試 → 上線

另一條平行但同樣會卡人的是：

環境建置 → 轉檔切片管線 → 閱讀串流 → 閱讀器 ／ 首批內容上架
轉檔管線同時擋住閱讀串流與內容上架兩件事，是最容易被低估的工項。

9.3 估算的前提（任何一條不成立都要重估）

  1. 人力：前端 2 人、漫畫館後端 2 人、平台後端 1 人（遊戲站團隊支援）、設計 1 人、QA 1 人、營運 1 人。
  2. 設計稿在 W3 前交付完整的手機版，PC 版可以晚到 W11。
  3. 現有錢包可以在 8 人日內加上冪等扣款與退款（如果要從頭改金流，這個數字會翻倍）。
  4. 首批內容以單行本為主，連載為次要。
  5. PC 版與手機版同時上線。
  6. 未包含：Peachy Party、留言功能、PWA、跨裝置進度同步、題材榜。

11上線前的技術檢查

  • 折抵金額由後端重算；券的核銷要後端驗證；擋過期券。
  • 書櫃、歷史紀錄、優惠券改接會員 API；收藏與兌換碼接 API。
  • 作品的最近更新日與語言換成真實欄位，否則書櫃的「最近更新」排序與卡片上的更新日都是假的。
  • 「已解鎖 N / M 話」的 M 會隨連載更新變動，要以後端回傳的最新話數為準。
  • 已購量大時，書櫃要改分頁載入或無限捲動。
  • 列表與搜尋改接後端分頁。
  • 作品下架／授權到期的已購作品要有標示與說明文案；退款／撤銷購買後書櫃要即時移除。
  • 未登入時點收藏／進會員中心要導登入。
  • REVERSED 訂單要能在對帳報表查出來。
